# Fatigue

疲労は社員の稼働量によって週ごとに変化する状態で、基本スキルとは独立して生産性へ影響します。

## 状態と計算

`Employee.Fatigue`は`decimal`の0〜100。通常の初期値は0で、コンストラクタの`initialFatigue`で範囲内の値を指定できます。範囲外は例外となり、公開setterはありません。

副作用のない`FatigueCalculator`が次の計算を担当します。

```text
実勤務時間 = WeeklyAvailableHours - AvailableHours
稼働率 = 実勤務時間 / WeeklyAvailableHours
翌週の疲労 = clamp(現在の疲労 + 40 × (稼働率 - 0.75), 0, 100)
疲労倍率 = 1 - 0.5 × (疲労 / 100)
進捗 = 実勤務時間 × 基本スキル倍率 × 疲労倍率
```

週40h勤務可能な社員は、無割当で-30、10hで-20、20hで-10、30hで変化なし、40hで+10となります。週の利用可能工数が異なっても、同じ稼働率なら疲労増減量は同じです。

疲労0/50/100の倍率は1/0.75/0.5。Backend: 4のみを持つ社員がBackendImplementationへ10h勤務した場合の進捗は、それぞれ12/9/6h相当です。スキルの値や実際の消費勤務時間は疲労で変わりません。

計算は`decimal`の有限精度で行い、表示用などの明示的な桁丸めは追加しません。割り切れない除算などではdecimalの精度限界による丸めが発生します。たとえば週3h・実勤務1h・初期疲労50の計算結果は、厳密な分数値ではなくdecimalで表現可能な近似値になります。任意の入力で進捗の分割・加算順が厳密に同じ値になることは保証しません。

計算への範囲外の疲労、0以下の週の利用可能工数、負または週の利用可能工数を超える実勤務工数は`ArgumentOutOfRangeException`で拒否します。

## 週次の更新順序

1. `WeekProcessor`が更新前の疲労と週送り時点のスキルで、全タスクの進捗を反映する。
2. `GameSimulation`が各社員の`CompleteWeek()`を一度ずつ呼ぶ。
3. 社員が消費勤務時間から翌週の疲労を更新し、利用可能工数をリセットする。
4. シミュレーションが割当をクリアし、週番号を進める。

今週の稼働による疲労変化は翌週から効きます。疲労の更新は週の消費勤務時間の合計を使うため、タスクの処理順や週内の割当の分割数に依存しません。無割当の社員も回復します。完了量を超えた進捗が破棄されても、消費済み勤務時間は疲労の計算対象になります。

公開の工数消費は`GameSimulation.TryAllocateHours`経由に限定します。`Employee.TryConsumeHours`は内部用、`ResetWeeklyHours`はprivateで週末更新からのみ呼ばれ、外部操作による疲労の回避や週内の工数再充填を防ぎます。

たとえば基本スキル倍率1・疲労0の社員が40hずつ連続勤務すると、1週目の進捗は40、週末の疲労は10。2週目は疲労10で進捗38となり、週末の疲労は20になります。

## バランス調整

`FatigueCalculator`のバランス係数は`NeutralUtilization`(0.75)、`ChangePerUtilization`(40)、`MinProductivityMultiplier`(0.5)です。private constで定義しており、調整にはソースコードの変更とテストの更新が必要です。実行時の設定差替え機能はありません。

`MinFatigue`(0)と`MaxFatigue`(100)は疲労状態の有効範囲を定義するドメイン上の制約です。

`WeeklyAvailableHours`は週の割当上限です。現在の中立稼働率は、上限まで連続勤務すると疲労が蓄積する設計です。契約勤務時間や残業の概念はまだ扱いません。残業導入時の中立点は、その機能と併せて別途検討します。

残業、休暇、個別スキル、AI補正、スキル成長、UIは本機能の対象外です。
