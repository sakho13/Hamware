# ProductHealth

プロダクト全体の技術的負債と品質を、社員の能力とは独立した継続状態として扱います。

## 状態と所有

- `ProductState.TechnicalDebt` / `Quality` は `decimal`、範囲はそれぞれ0〜100。初期値は負債10・品質70。
- `new GameSimulation(initialTechnicalDebt: 0m, initialQuality: 70m)` のように開始時の状態を指定できる。範囲外の初期値は例外とし、黙って丸めない。
- 各シミュレーションが自身の状態を新規生成し、`GameSimulation.Product` から参照できる。公開setter・任意更新・状態差替えは提供しない。
- `ProductState` 自身が週次の増減を受け取り、上下限を守る。更新操作はシミュレーション内部用に限定する。
- 負債と品質は独立して増減する。品質は今回、健全性指標として保持する。品質による生産性・障害・顧客満足度への補正は実装していない。

## 完了効果

当週の `WeekProcessor` による進捗反映で未完了から完了になったタスクについて、一度だけ次の効果を集計します。

```text
負債増減 = RequiredProgressHours × 負債係数
品質増減 = RequiredProgressHours × 品質係数
翌週の状態値 = clamp(現在値 + 当週完了した全タスクの増減合計, 0, 100)
```

係数は必要進捗1h相当あたりの増減です。実勤務時間、完了週だけの進捗、完了に不要な超過進捗では計算しません。同規模の仕事を分割しても全完了時の効果の合計は同じです。ただし、完了時期や上下限への到達が異なると週ごとの状態は変わります。

| TaskType | 負債係数 | 品質係数 | 負債の進捗影響 |
|---|---:|---:|---|
| FrontendImplementation | +0.10 | -0.05 | あり |
| BackendImplementation | +0.10 | -0.05 | あり |
| Database | 0 | 0 | あり |
| Infrastructure | 0 | 0 | あり |
| Testing | 0 | +0.20 | なし |
| Security | 0 | +0.10 | なし |
| Architecture | -0.20 | +0.05 | なし |
| Planning | 0 | 0 | なし |
| Management | 0 | 0 | なし |
| CustomerSupport | 0 | 0 | なし |

必要進捗20h相当の機能実装を完了すると負債+2・品質-1。Testingなら品質+4、Architectureなら負債-4・品質+1となります。Database / Infrastructureは作業内容の幅が広いため、初期ルールでは完了効果を中立にしています。

未完了・無割当の週には状態は自然増減しません。完了済みタスクが一覧に残っていても再適用しません。`ApplyProgress()` で処理前に完了させたタスクへの遡及適用も行いません。

## 生産性

```text
開発系タスクの負債倍率 = 1 - 0.5 × (TechnicalDebt / 100)
その他のタスクの負債倍率 = 1
社員ごとの進捗 = 実勤務時間 × 基本スキル倍率 × 疲労倍率 × 負債倍率
```

開発系は上表の4種です。負債0/10/50/100で倍率は1/0.95/0.75/0.5となります。Testing / Security / Architectureは高負債でも改善作業へ取り組めるよう負債の影響対象から外しています。社員のスキル・疲労の補正は通常どおり受けます。

例：実勤務10h、スキル倍率1.4、疲労50で倍率0.75、負債50で倍率0.75なら進捗は7.875h相当です。割当は10hのままで、勤務時間・疲労を進捗から逆算しません。スキル値は書き換えません。

社員別に計算した進捗をタスク単位に合算します。明示的な桁丸めは追加せず、既存処理と同じ `decimal` の有限精度を使います。完了を超えた進捗を破棄し、勤務時間を返却しない仕様も維持します。

## 週次順序

1. `WeekProcessor` が開始時の負債から当週の倍率を固定する。
2. 全タスクの進捗をスキル・更新前疲労・当週の負債倍率で計算し、新規完了タスクの増減を集計する。
3. 全タスク処理後、合計増減を `ProductState` へ一度だけ渡し、状態値を上下限内へ制限する。
4. `GameSimulation` が各社員の週末処理を行い、疲労を更新してから勤務時間を復元する。
5. 割当をクリアし、週番号を進める。

当週の完了で変わった負債は翌週の進捗から効きます。タスクを処理する順序によって、同じ週の他タスクの倍率を変えません。例えば負債99に+2と-4の完了効果がある場合、合算して97にします。タスクごとに上下限を適用すると、順序によって結果が変わるためです。

## 複数週の例

週40h勤務可能、Frontend / Architecture / Testingの各スキル2を持つ社員が、毎週20h勤務する例です。スキル倍率1・疲労0で負債の変化を比較できます。

| 週 | 作業 | 当週進捗 | 週末負債 | 週末品質 |
|---|---|---:|---:|---:|
| 1 | 必要進捗19のFrontendタスクを完了 | 19 | 11.9 | 69.05 |
| 2 | 次の必要進捗100のFrontendタスクを進める | 18.81 | 11.9 | 69.05 |
| 3 | 必要進捗20のArchitectureタスクを完了 | 20 | 7.9 | 70.05 |
| 4 | 第2週のFrontendタスクを進める（累積38.02、未完了） | 19.21 | 7.9 | 70.05 |
| 5 | 必要進捗20のTestingタスクを完了 | 20 | 7.9 | 74.05 |

改善へ工数を割いた週には機能が進みませんが、その翌週には同じ20hで得られる機能進捗が増えます。

## 調整箇所と対象外

- 初期値・値域は `ProductState`、最低進捗倍率は `ProductHealthCalculator` の定数で管理する。
- 種別ごとの係数と負債影響対象は、不変な `TaskProductProfile` と `TaskProductProfiles` に集約する。
- いずれも調整にはソース変更とテストが必要。実行中の設定変更画面・設定ファイル基盤は追加していない。
- 特定技術ごとの負債、個別スキル、本番障害、問い合わせ、顧客満足度、技術選定、複数プロダクト管理、保存・復元、UIは対象外。
